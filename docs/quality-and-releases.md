# Quality and releases

Every push and pull request runs the Verify workflow. A main-branch application change must increase the version and add user-facing notes. Publishing waits for both application and Mac packaging jobs to pass; a failed check cannot publish a new build.

## Feature checklist

1. Add regression coverage for changed behavior: success, failure, saving/reopening, and cancellation where relevant. Keep low-impact styling changes under visual review.
2. Run the appropriate local checks. Review narrow and wide layouts, keyboard focus, light/dark colors, error recovery, and empty states. Remove repeated implementation explanations from everyday screens.
3. Run `python scripts/release.py bump --note 'Describe the improvement for a user.'`. Refine the new CHANGELOG section; group notes under Added, Improved, or Fixed. The command synchronizes all package versions.
4. Commit the feature and notes together. Open a pull request; fix failing checks before merging.
5. After merging to main, Verify builds the Mac package, checks signatures/resources, attaches checksums, creates the version tag, and publishes the release automatically. A version already published is never overwritten.

## Automated checks

- Python API/storage/interview tests and real GCC/Clang execution inside Docker. `FORGEPAD_REQUIRE_DOCKER=1` makes an unavailable runner fail CI instead of skipping execution tests.
- Rust persistence, draft conflict handling, question privacy, activity/timezones, interview replay, and MCP transport/security tests.
- React component and keyboard tests, TypeScript production compilation, dependency audit, Rust formatting and Clippy.
- Browser → native Rust service → packaged worker → Docker → persisted progress tests. These use a disposable workspace and never modify personal progress.
- Official MCP SDK interoperability against the actual connector.
- Release bundle resource validation and macOS signature verification.

To run browser checks locally after building the service:

```sh
cargo build --locked --manifest-path src-tauri/Cargo.toml --no-default-features --bins
npx --prefix frontend playwright install chromium
FORGEPAD_QA_PYTHON="$PWD/.venv/bin/python" npm run test:e2e --prefix frontend
```

Set `DOCKER_CONTEXT` and `FORGEPAD_RUNNER_TMPDIR` if the local VM requires a particular connection or shared folder. To test a freshly packaged worker, set `FORGEPAD_WORKER` to the sidecar generated by `npm run native:prepare`. Failure screenshots and traces are retained as workflow artifacts.

## Signing

The default release is ad-hoc signed and explicitly described that way on its download page. A frictionless first launch requires an Apple Developer ID and notarization. Configure these repository secrets to enable it:

- `APPLE_CERTIFICATE`: base64-encoded Developer ID Application `.p12` certificate.
- `APPLE_CERTIFICATE_PASSWORD`: certificate password.
- `APPLE_SIGNING_IDENTITY`: full Developer ID Application identity.
- `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`: notarization account, app-specific password, and team.

The packaging script signs the compiler worker with its necessary Python library entitlement, signs the other helpers and app, notarizes/staples when configured, then creates the final archives. No signing credentials are stored in the repository. Missing credentials produce a clearly labeled ad-hoc download, never a false notarization claim.

## Manual hardware checks

Microphone permission prompts, actual Parakeet transcription accuracy/latency, and external HeyClicky client permissions need a real Mac and downloaded speech model. Unit tests and helper builds do not establish speech quality. Before calling voice production-ready, dictate a representative technical answer, check partial text and corrections, navigate away while recording, and confirm the microphone stops.
